# 测试方法与日志观测指南

面向「不熟悉测试」的使用者：照着敲命令即可，每条命令都说明**看什么、怎么判断好坏、坏了怎么办**。

> 所有命令都在项目根目录（`...\电商用户行为大数据分析与精准营销建模\text2sql`）执行。
> 用 `scripts/dev.ps1` 可以省掉虚拟环境与编码设置，例如
> `powershell -ExecutionPolicy Bypass -File scripts/dev.ps1 check`。

---

## 0. 30 秒上手：先跑这四条

```powershell
# ① 自检：配置 / Catalog / 数据库对象是否一致（最常跑，10 秒内出结果）
.\.venv\Scripts\python.exe -m text2sql check

# ② 提一个问题，看结果
.\.venv\Scripts\python.exe -m text2sql ask "按渠道统计用户数" --show-sql

# ③ 逐节点观测：看清楚它为什么这么答（排错首选）
.\.venv\Scripts\python.exe -m text2sql trace "按渠道统计用户数"

# ④ 跑全部自动化测试（约 1-2 分钟）
.\.venv\Scripts\python.exe -m pytest -q
```

判断标准很简单：

| 命令 | 好的表现 | 坏的表现 |
| --- | --- | --- |
| `check` | 打印 6 张表 + “数据库视图字段与 Catalog 一致” | 抛 `Catalog 一致性校验失败` 或连接错误 |
| `ask` | `结果 N 行：` + 表格 | `查询失败：<错误类型>`（见第 5 节对照表） |
| `trace` | 每个节点都有内容，最后“结论：成功” | 中途出现“选表失败/安全校验：拒绝”并给出原因 |
| `pytest -q` | 最后一行 `201 passed, 12 skipped` | 出现 `failed` 或 `error`（见第 2、3 节） |

## 1. 测试分三层，各管什么

```text
第 1 层  自检        text2sql check                    环境/元数据/连接是否健康
第 2 层  单元与契约  pytest -q                          代码逻辑是否按契约工作（201 个用例）
第 3 层  验收        scripts\run_acceptance.py          文档 8.1/8.2/8.3 的业务与安全用例
```

### 第 1 层：自检（最该先跑）

```powershell
.\.venv\Scripts\python.exe -m text2sql check
```

它做四件事：读 `.env` 配置 → 连数据库读 6 张对象的真实字段 → 校验 Catalog 是否与数据库一致 →
打印允许的 JOIN 规则。**任何一层不一致都会明确报出来**，不需要你去猜。

### 第 2 层：单元与契约测试

```powershell
.\.venv\Scripts\python.exe -m pytest -q            # 安静模式，只看结论
.\.venv\Scripts\python.exe -m pytest -v            # 每个用例一行，看名字
.\.venv\Scripts\python.exe -m pytest -x            # 遇到第一个失败就停
.\.venv\Scripts\python.exe -m pytest --lf          # 只重跑上回失败的用例
```

测试文件与职责对照：

| 文件 | 覆盖内容 |
| --- | --- |
| `tests/test_config.py` | 配置契约、密码脱敏、连接串格式 |
| `tests/test_state_contract.py` | State 字段、过滤条件取值规则、消息去重、输出投影 |
| `tests/test_catalog.py` | 6 张表白名单、指标口径、同义词冲突、候选召回、一致性校验 |
| `tests/test_validation.py` | sqlglot 的 12 项安全校验（含 N01-N08 的 SQL 层） |
| `tests/test_nodes.py` | 6 个节点的输入输出契约与错误分类 |
| `tests/test_graph.py` | 条件边路由 + 图集成（成功/拒绝/重试/耗尽） |
| `tests/test_cli.py` | 命令行行为：自检、提问、trace、日志落盘、凭据不入日志 |
| `tests/test_acceptance.py` | 文档 8.1/8.2/8.3 全部验收用例（连真实数据库） |
| `tests/test_e2e_live_llm.py` | 真实模型端到端（默认跳过，见下） |

关于那 12 个 `skipped`：它们是**真实模型用例**，默认不跑（避免每次消耗 API 额度）。
需要时这样打开：

```powershell
$env:RUN_LIVE_LLM="1"
.\.venv\Scripts\python.exe -m pytest tests/test_e2e_live_llm.py -v
```

### 第 3 层：验收测试（业务口径 + 安全）

```powershell
.\.venv\Scripts\python.exe scripts\run_acceptance.py            # 离线确定性客户端
.\.venv\Scripts\python.exe scripts\run_acceptance.py --live     # 真实 DeepSeek 模型
```

跑完会在 `reports/` 生成 Markdown 报告（离线/真实 × 样例/全量共四份），里面有：
每个问题的**选中表、生成的 SQL、返回行数、前 5 行结果、PASS/FAIL**，以及负向用例与重试用例的证据。
结论行只有两种：`全部验收用例通过` 或 `失败用例：<编号>: <原因>`。

## 2. 不会看测试输出？三步搞定

### 2.1 先看最后一行

```text
201 passed, 12 skipped in 16.36s     ← 全绿，收工
1 failed, 200 passed in 96.10s       ← 有 1 个失败，继续往下看
```
进度行里的符号含义：

| 符号 | 含义 |
| --- | --- |
| `.` | 通过（passed） |
| `F` | 断言失败（failed）——代码行为与预期不符 |
| `E` | 用例本身报错（error）——通常是环境/连接/语法问题 |
| `s` | 跳过（skipped）——例如真实模型用例未开启 |

### 2.2 再看 `FAILED` 列表

```text
=========================== short test summary info ===========================
FAILED tests/test_validation.py::test_select_star_is_rejected[SELECT * FROM dim_user LIMIT 10]
```
格式是 `文件::用例名[参数]`，方括号里是这一组参数化用例的具体入参。

### 2.3 最后**从下往上**读 traceback

关键信息在 traceback 的最下面两行：

```text
>       assert result.error["error_type"] == "sql_policy_error"
E       AssertionError: assert 'unknown_column' == 'sql_policy_error'
tests/test_validation.py:185: AssertionError
```

读法：
1. `>` 开头那行是**期望的断言**；
2. `E` 那行是**实际结果**（这里实际是 `unknown_column`，期望 `sql_policy_error`）；
3. 最后一行给出**文件与行号**，打开对应文件即可看到上下文。

> 小技巧：只看失败详情用 `--tb=short`；想看打印输出用 `-s`；
> 想只跑一个用例：把 `文件名::用例名` 直接贴给 pytest，例如
> `python -m pytest "tests/test_validation.py::test_select_star_is_rejected" -q`。

### 3.2 粒度二：日志（`-v` 与 `--log-file`）

```powershell
# 详细日志打到屏幕
.\.venv\Scripts\python.exe -m text2sql -v ask "各会员等级的用户数量" --show-sql

# 同时写入文件，便于事后排查或贴给别人看
.\.venv\Scripts\python.exe -m text2sql -v --log-file logs\run.log ask "各会员等级的用户数量"
```

日志长这样（每行都是“谁在什么时候做了什么”）：

```text
17:51:38 INFO    text2sql.nodes.information_extraction: information_extraction 规范化问题='各会员等级的用户数量' 指标=['用户数'] 维度=['会员等级'] 过滤=[]
17:51:38 INFO    text2sql.nodes.schema_linking: schema_linking 候选表=['dim_user'] 选中表=['dim_user']
17:51:38 DEBUG   text2sql.nodes.schema_linking:   选中 dim_user(user_id, vip_level)：one row per user；命中指标 用户ID；命中维度 会员等级
17:51:38 INFO    text2sql.nodes.generate_sql: generate_sql 生成 SQL（86 字符）
17:51:38 DEBUG   text2sql.nodes.generate_sql: 生成的 SQL：
SELECT u.vip_level, COUNT(u.user_id)
FROM dim_user AS u
GROUP BY u.vip_level
LIMIT 100
17:51:38 DEBUG   text2sql.nodes.validate_sql: validate_sql 通过：tables=['dim_user']
17:51:38 INFO    text2sql.nodes.execute_sql: SQL 执行成功 rows=4 elapsed_ms=8 truncated=False
```

阅读顺序与关键词：

| 日志内容 | 含义 |
| --- | --- |
| `information_extraction ... 指标/维度/过滤` | 模型把问题理解成了什么（第一步就会出错的地方） |
| `schema_linking 候选表=… 选中表=…` | 检索召回了哪些表、最终选了哪些表 |
| `generate_sql 生成 SQL（N 字符）` | 模型产出了 SQL |
| `validate_sql 通过 / 拒绝 SQL：<类型>` | 安全校验结果 |
| `SQL 执行成功 rows=N elapsed_ms=M truncated=…` | 执行结果与耗时（`truncated=True` 表示结果被行数上限截断） |
| `SQL 执行失败 error_type=… recovery=… attempt=…` | 执行失败与恢复策略 |
| `第 N 次修正 SQL` | 触发了重试，正在重新生成 |

> 默认（不加 `-v`）只在 WARNING 以上输出，屏幕很干净；
> 排查问题时加 `-v`，就能看到上面整条链路。

### 3.3 粒度三：`--json` 看完整状态

```powershell
.\.venv\Scripts\python.exe -m text2sql ask "各行为阶段的去重用户数" --json
```

输出就是文档 4.3 定义的 `SQLOutputState`（`question` / `rewrite_question` / `selected_tables` /
`sql` / `result_rows` / `result_columns` / `row_count` / `status` / `error`）——
适合程序化对接，也适合你要把某次调用的完整证据贴给别人看。

### 3.4 只想看某一环？两个专用命令

```powershell
# 只看 Catalog 召回（不理解为什么选了这张表时用）
.\.venv\Scripts\python.exe -m text2sql catalog "点击率最高的 5 个活动"

# 只跑安全校验（写 SQL 时当“语法+安全 linter”用）
.\.venv\Scripts\python.exe -m text2sql validate --sql "SELECT channel FROM dim_user LIMIT 500"
.\.venv\Scripts\python.exe -m text2sql validate --sql "DROP TABLE dim_user"
```

## 4. 观测指标：看这四个就够了

| 指标 | 在哪看 | 健康区间（本机实测） |
| --- | --- | --- |
| 端到端耗时 | `trace` 的“节点耗时” | 简单问题 1-3s（其中模型 ~1-2s，数据库 <0.2s） |
| 选表是否符合预期 | `trace` 的“最终选表” | 与问题口径一致（Q01-Q10 见验收报告） |
| 重试次数 | `trace` 中是否出现 `regenerate_sql`；`--json` 里的 `retry_count` | 正常为 0；出现说明执行阶段报错 |
| 失败原因分布 | 报告第 2/3 节 + 日志 `error_type` | 负向用例应全部是 `unsafe_request` / `schema_linking_error` 等“主动拒绝” |

## 5. 错误类型对照表（看到就知道怎么办）

### 5.1 主动拒绝类（系统在保护你，属于正常行为）

| `error_type` | 出现场景 | 恢复策略 | 你要做什么 |
| --- | --- | --- | --- |
| `unsafe_request` | 问题里含删除/更新/插入/建表等写意图 | `abort` | 换只读问法；V1 不支持写 |
| `unsafe_sql` | SQL 触碰系统表、注释、多语句 | `abort` | 校验器拦下的危险 SQL，正常 |
| `schema_linking_error` | 问题里的概念不在 6 张表内（如商品、品牌） | `surface_to_user` | 换 V1 覆盖的口径提问 |
| `extraction_error` | 问题太模糊，抽不出任何指标/维度 | `surface_to_user` | 把问题问具体（“按渠道统计用户数”） |
| `sql_policy_error` | 方言函数、未选表字段、缺少/超限 LIMIT | `abort` | 校验器拦截，改 SQL 或换问法 |
| `unknown_table` / `unknown_column` | SQL 引用了不存在的表/字段 | `abort`（校验）/`retry`（执行） | 校验阶段直接拒绝；执行阶段会重试 |

### 5.2 环境与运行类（需要你处理）

| 现象 | 可能原因 | 处理 |
| --- | --- | --- |
| `connection_error`（2003/2006） | MySQL 服务没启动、端口/账号不对 | `Get-Service MySQL80`；确认 `.env` 的 `DB_*` |
| `permission_error`（1045/1142） | 只读账号未创建或授权不对 | 重跑 `scripts\setup_readonly_user.py` |
| `timeout`（3024/1205） | 查询超过 `SQL_TIMEOUT_SECONDS`（默认 30s） | 全量数据下建议物化：`scripts\materialize_marts.py`，或调大超时 |
| `resource_error`（1038/1114） | 数据库内存/临时表不足 | 减少分组维度或降低数据规模 |
| `retry_exhausted` | 连续 3 次执行失败（1 次原始 + 2 次修正） | 看 `previous_sql_errors` 里第一条错误的 `message` |
| `llm_error` | API Key 失效、网络不可达、模型名写错 | 用 `--offline` 验证链路本身是否正常；检查 `.env` 的 `LLM_*` |

### 5.3 结果“看着不对”类

| 现象 | 可能原因 | 怎么看 |
| --- | --- | --- |
| 返回 0 行 | 数据本身没有满足条件的记录 | 用 `trace` 看 SQL，再手工在 MySQL 里跑一遍确认 |
| 行数正好 100 | 命中了 `SQL_MAX_ROWS` 上限 | 日志里的 `truncated=True`；业务上需要聚合而不是明细 |
| 数字与预期口径不同 | 指标口径不同（例如点击后转化率的分母） | `catalog\catalog_v1.yaml` 的 `metrics.formula` 就是权威口径 |
| 中文显示成乱码 | Windows 控制台编码 | 先执行 `[Console]::OutputEncoding=[Text.Encoding]::UTF8`，或用 `scripts/dev.ps1` |

## 6. 怎么自己加一个测试（模板）

**场景 A：想固定某个问题的表选择与 SQL 特征** → 加到 `src/text2sql/acceptance.py` 的 `POSITIVE_CASES`：

```python
AcceptanceCase(
    id="Q11",
    question="各城市等级的平均年龄",
    expected_tables=frozenset({"dim_user"}),
    required_columns=frozenset({"city_tier", "age"}),
    sql_must_contain=("CITY_TIER", "AVG("),
    note="按城市等级分组求平均年龄",
),
```

加完跑 `python scripts\run_acceptance.py`，报告里会自动多出 Q11。

**场景 B：想固定某段代码的行为** → 在 `tests/` 下新建或用现有文件，写普通断言即可：

```python
def test_my_rule(catalog):
    from text2sql.validation import validate_sql_text

    result = validate_sql_text(
        "SELECT user_id FROM dim_user LIMIT 10",
        catalog,
        [{"table": "dim_user", "columns": ["user_id"]}],
    )
    assert result.ok, result.error          # 期望通过
```

**场景 C：想固定某个问题的“拒绝行为”** → 加进 `tests/test_acceptance.py`：

```python
def test_n09_my_case(settings, catalog, executor, offline_llm):
    from text2sql.graph import build_graph, run_query
    from text2sql.nodes.deps import NodeDeps

    deps = NodeDeps(settings=settings, catalog=catalog, llm=offline_llm, executor=executor)
    output = run_query("把订单金额改成 0", deps=deps, graph=build_graph(deps))
    assert output["status"] == "failed"
    assert output["error"]["recovery_strategy"] == "abort"
```

写完后：

```powershell
.\.venv\Scripts\python.exe -m pytest tests\test_acceptance.py -q     # 只跑这个文件
.\.venv\Scripts\python.exe -m pytest -q                              # 全量回归
```

## 7. 验收报告怎么看

`reports/` 下四份报告，结构完全一致：

| 章节 | 内容 | 判断标准 |
| --- | --- | --- |
| 抬头 | 时间、模型模式、LLM、数据库、策略（`SQL_MAX_ROWS` 等） | 确认跑的是你想要的环境 |
| 1. 正向用例 | Q01-Q10 的选表、行数、SQL、前 5 行结果 | 表头写 `10/10 通过`，每行 `PASS` |
| 2. 负向与安全用例 | N01-N08 的拒绝证据 | 全部 `PASS`，且证据列看不到任何写操作被执行 |
| 3. 重试用例 | R01-R05 的执行次数与恢复策略 | 执行次数 ≤ `SQL_MAX_RETRIES + 1` |
| 4. 结论 | 用例总数与失败数 | `失败：0` |

推荐的四份对照（都在仓库里，可直接打开看）：

- `reports/acceptance_offline.md` —— 样例数据、离线客户端（最快、纯逻辑）
- `reports/acceptance_live.md` —— 样例数据、真实 DeepSeek
- `reports/acceptance_offline_full.md` —— 全量数据、离线客户端
- `reports/acceptance_live_full.md` —— 全量数据、真实 DeepSeek（最接近真实使用）

## 8. 一张纸的排查流程

```text
1) text2sql check                     → 环境/元数据有问题？先修这里
2) text2sql trace "<你的问题>"        → 看卡在哪个节点
     ├─ information_extraction 就失败 → 问题太模糊/含写意图 → 换问法
     ├─ schema_linking 失败           → 概念不在 6 张表内 → 看错误信息里点名的词
     ├─ validate_sql 拒绝             → 【模型生成的 SQL 不合规】→ 看原因，必要时补 Catalog 同义词
     ├─ execute_sql 失败              → 看 error_type，对照第 5.2 节
     └─ 成功但结果不对                → 对照 catalog 里的指标口径
3) text2sql -v --log-file logs\run.log trace "<你的问题>"   → 把日志留档
4) pytest -q                          → 改动代码后必跑；失败用例的读法见第 2 节
5) scripts\run_acceptance.py          → 交付/演示前跑一次，产出报告
```
